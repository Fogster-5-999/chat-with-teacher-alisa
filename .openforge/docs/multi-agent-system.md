# Мульти-агентная система OpenForge

## 1. Назначение системы

Мульти-агентная система предназначена для автоматизации задач разработки программного обеспечения через коллаборацию специализированных ИИ-агентов. Каждый агент отвечает за свою дисциплину: планирование, архитектуру, реализацию, контроль качества, безопасность, производительность и документацию.

**Область применения:** любые проекты, где используется OpenCode в качестве редактора/CLI.

## 2. Архитектура

### 2.1. Состав агентов

| Агент | Модель | Режим | Ответственность |
|-------|--------|-------|-----------------|
| Orchestrator | DeepSeek V4 Flash Free | primary (Tab) | Маршрутизация задач, сплит, мерж |
| Planner | DeepSeek V4 Flash Free | subagent (@planner) | Декомпозиция, оценка сложности, порядок |
| Architect | DeepSeek V4 Flash Free | subagent (@architect) | Архитектура, контракты, структура папок |
| Logic | DeepSeek V4 Flash Free | subagent (@logic) | Алгоритмы, бэкенд, игровая логика |
| UI | North Mini Code Free | subagent (@ui) | HTML, CSS, React/Vue, анимации, a11y |
| QA | DeepSeek V4 Flash Free | subagent (@qa) | Баги, edge cases, предлагает fix-код |
| Performance | MiMo V2.5 Free | subagent (@performance) | FPS, память, бандл, сеть, GC |
| Security | MiMo V2.5 Free | subagent (@security) | XSS, SQLi, инъекции, утечки секретов, auth |
| Documentation | MiMo V2.5 Free | subagent (@documentation) | README, API docs, ченжлоги, миграции |

### 2.2. Pipeline выполнения

```
Пользователь → Orchestrator → Planner → Architect
  → Logic ──┐
  → UI    ──┤ (параллельно)
  → Performance → QA → Security → Documentation
  → если найдены проблемы → возврат к Logic/UI
  → Мерж → Пользователь
```

**Параллельное выполнение:** Logic и UI запускаются одновременно через отдельные вызовы Task. Все остальные агенты выполняются последовательно.

**Feedback loop:** если после QA, Security или Performance обнаружены проблемы — Orchestrator создаёт новую подзадачу для Logic или UI на исправление. Цикл повторяется до 3 раз, затем эскалация пользователю.

### 2.3. Права доступа

| Агент | read | edit | bash | glob | grep |
|-------|------|------|------|------|------|
| Orchestrator | allow | allow | allow | allow | allow |
| Planner | allow | deny | deny | allow | allow |
| Architect | allow | deny | deny | allow | allow |
| Logic | allow | allow | allow | allow | allow |
| UI | allow | allow | allow | allow | allow |
| QA | allow | deny | deny | allow | allow |
| Performance | allow | deny | deny | allow | allow |
| Security | allow | deny | deny | allow | allow |
| Documentation | allow | allow | allow | allow | allow |

Агенты аудита (QA, Performance, Security) имеют права только на чтение — они анализируют код, но не могут его изменять. Исправления вносятся через Orchestrator, который направляет задачу Logic или UI.

## 3. Конфигурация

### 3.1. Файлы конфигурации

- **Локальная (проект):** `{project}/opencode.jsonc`
- **Глобальная:** `~/.config/opencode/opencode.jsonc`

Локальная конфигурация переопределяет глобальную. Для проекта OpenForge используется только локальная.

### 3.2. Структура opencode.jsonc

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "model": "opencode/deepseek-v4-flash-free",
  "agent": {
    "orchestrator": {
      "mode": "primary",              // основной агент при нажатии Tab
      "model": "opencode/deepseek-v4-flash-free",
      "temperature": 0.2,
      "permission": { /* полные права */ },
      "prompt": "{file:./.agents/orchestrator.md}"
    },
    "planner": {
      "mode": "subagent",             // вызывается через @planner
      "edit": "deny",                 // не меняет файлы
      "bash": "deny"                  // не запускает команды
    }
  }
}
```

### 3.3. Промпты агентов

Каждый агент имеет собственный промпт-файл в `.agents/`:

- `.agents/orchestrator.md`
- `.agents/planner.md`
- `.agents/architect.md`
- `.agents/logic.md`
- `.agents/ui.md`
- `.agents/qa.md`
- `.agents/performance.md`
- `.agents/security.md`
- `.agents/documentation.md`

## 4. Режимы работы

### 4.1. Быстрый режим (small fix)

Применяется для исправлений, затрагивающих 1-2 файла и менее 50 строк кода.

**Pipeline:** Logic только. Planner, Architect, Performance, QA, Security, Documentation пропускаются.

**Запуск:** Orchestrator принимает решение о выборе режима на основе сложности задачи.

### 4.2. Полный режим (full pipeline)

Применяется для новых фич, рефакторинга, изменений в архитектуре.

**Pipeline:** полный, как описано в разделе 2.2.

### 4.3. Прямой вызов агента

Любой агент может быть вызван напрямую через @mention:

- `@planner распиши задачу`
- `@qa найди баги в этом коде`
- `@security проверь безопасность`

Агент выполнит задачу в контексте текущего проекта, минуя основной pipeline.

## 5. Процесс выполнения задачи (полный режим)

### 5.1. Планировщик (Planner)

- Декомпозиция задачи на шаги
- Оценка сложности и количества файлов
- Список рисков и зависимостей
- Порядок выполнения

**Вход:** запрос пользователя
**Выход:** план с шагами, оценками, рисками

### 5.2. Архитектор (Architect)

- Проектирование архитектуры
- Граф зависимостей, управление состоянием
- API контракты, структура папок
- Выявление технического долга

**Вход:** план от Planner
**Выход:** архитектурное решение

### 5.3. Реализация (Logic + UI — параллельно)

**Logic:**
- Реализация алгоритмов, бизнес-логики
- Бэкенд, игровая физика, AI
- Обработка данных, мутации состояния

**UI:**
- HTML/CSS, компоненты React/Vue
- Анимации, адаптивная вёрстка, доступность
- Кросс-браузерная совместимость

**Вход:** архитектурное решение
**Выход:** диффы с реализацией

### 5.4. Аудит производительности (Performance)

- Анализ FPS, GC, утечек памяти
- Размер бандла, ленивая загрузка
- Кэширование, эффективность DOM

**Вход:** код от Logic + UI
**Выход:** список issues с приоритетами (P0-P3)

### 5.5. Контроль качества (QA)

- Поиск багов, edge cases, race conditions
- Проверка на dead code, необработанные ошибки
- Каждое issue сопровождается кодом исправления (FIX_SUGGESTION)

**Вход:** код + результаты Performance
**Выход:** issues с severity и fix-кодом

### 5.6. Аудит безопасности (Security)

- XSS, SQLi, unsafe eval
- Утечки секретов, path traversal
- Проблемы аутентификации, DoS
- Риски зависимостей

**Вход:** код + результаты всех предыдущих шагов
**Выход:** issues с severity и вектором атаки

### 5.7. Документация (Documentation)

- Обновление README
- API документация
- Ченжлоги, руководства по миграции
- Инструкции по установке

**Вход:** итоговый дифф
**Выход:** обновлённые документы

### 5.8. Обработка ошибок

- **Таймаут/ошибка агента:** одна автоматическая попытка повтора
- **Повторный сбой:** агент пропускается с документированием причины
- **Critical-баги от QA:** пайплайн останавливается, задача возвращается Logic до перехода к Security
- **Эскалация:** если ни один агент не справился — задача передаётся пользователю

### 5.9. Стратегия мержа

- Патчи собираются от всех агентов
- Конфликтующие изменения отклоняются (запрос к пользователю)
- Порядок применения: Logic → UI → Documentation
- Финальная валидация: проверка на регрессии, сломанные импорты

## 6. Метрики и рекомендации

### 6.1. Лимиты контекста

- Каждый агент получает только:
  - Свой вход (результат предыдущего агента в сжатом виде)
  - Список файлов для изменения (не весь проект)
  - Контекст задачи (запрос пользователя)

### 6.2. Когда какой режим выбирать

| Ситуация | Режим |
|----------|-------|
| Фикс бага в 1 файле | Быстрый (Logic only) |
| Добавление простой функции | Logic + UI |
| Новая архитектурная фича | Полный pipeline |
| Аудит существующего кода | @qa / @security / @performance напрямую |

### 6.3. Рекомендации по экономии токенов

- Не передавать полный output предыдущего агента — только summary
- Audit-агенты читают только файлы из diff, не весь проект
- Documentation запускается только если были изменения в публичных API

## 7. Известные ограничения

### 7.1. Архитектурные

- Feedback loop ограничен 3 итерациями
- Cross-agent кэш не реализован (каждый агент читает файлы заново)
- Agent pruning выполняется Orchestrator-ом субъективно, без формальных критериев

### 7.2. Операционные

- Дублирование чтения файлов между агентами
- При параллельном запуске Logic + UI оба могут редактировать одни и те же файлы
- Нет мониторинга расхода токенов на уровне системы

### 7.3. Модельные

- North Mini Code Free (UI) уступает DeepSeek в сложных сценариях
- MiMo V2.5 Free (Performance/Security/Documentation) даёт поверхностный анализ

## 8. Правила разработки агентов

### 8.1. Общие правила

- Общение между агентами — на английском
- Ответ пользователю — на его языке
- Запрещено повторять контекст
- Запрещено выводить неизменённый код
- Запрещено перезаписывать целые файлы
- Предпочитать unified diff
- Не гадать — проверять из репозитория
- Dynamic project discovery обязательна
- Сохранять обратную совместимость

### 8.2. Quality checklist

Перед завершением каждый агент проверяет:

- [ ] Код собирается
- [ ] Тесты проходят
- [ ] Нет архитектурных нарушений
- [ ] Нет дублирования кода
- [ ] Нет новых зависимостей без согласования
- [ ] Обратная совместимость сохранена
- [ ] Патч минимален
- [ ] Нейминг консистентен
- [ ] Документация обновлена (если требуется)

### 8.3. Token saving rules

- Не выводить неизменённый код
- Не выводить полные файлы
- Не суммаризировать репозиторий
- Не повторять промпт
- Максимум: 250 слов
- Максимум: 1 патч на сообщение
- Максимум: 5 маркеров
- Если задача простая — отвечать в пределах 500 токенов

## 9. Примеры использования

### 9.1. Быстрый сценарий: исправление бага

```
Пользователь: "Почини деление на ноль в calc.ts"
Оркестратор: выбирает fast-path
Pipeline: Logic only
Logic: находит строку `return a / b` → добавляет проверку на 0
Результат: 1 файл изменён, 3 строки добавлено, ~200 токенов
```

### 9.2. Полный сценарий: новая страница

```
Пользователь: "Добавь страницу профиля с формой редактирования"
Оркестратор: выбирает full pipeline
Pipeline: Planner → Architect → Logic + UI → Performance → QA → Security → Docs
Результат: 5 файлов, полный цикл контроля качества
```

### 9.3. Прямой вызов: аудит безопасности

```
Пользователь: "@security проверь авторизацию в auth.ts"
Security: анализирует файл, находит незакрытый endpoint
Вывод: SEVERITY: HIGH, VECTOR: unauthenticated PUT /api/user
```

## Приложение A: Файловая структура

```
{project}/
├── opencode.jsonc                  # конфигурация мульти-агента (единственный файл в корне)
└── .openforge/                     # всё остальное здесь
    ├── agents/
    │   ├── orchestrator.md         # промпт оркестратора
    │   ├── planner.md              # промпт планировщика
    │   ├── architect.md            # промпт архитектора
    │   ├── logic.md                # промпт разработчика логики
    │   ├── ui.md                   # промпт разработчика UI
    │   ├── qa.md                   # промпт QA-инженера
    │   ├── performance.md          # промпт перформанс-инженера
    │   ├── security.md             # промпт security-инженера
    │   └── documentation.md        # промпт технического писателя
    ├── docs/
    │   └── multi-agent-system.md   # документация системы
    ├── AGENTS.md                   # справочник по агентам
    ├── PROJECT_PROFILE.json        # профиль проекта
    ├── README.md                   # английская версия
    └── README.ru.md                # русская версия
```
